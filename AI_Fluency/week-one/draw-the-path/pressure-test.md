# Pressure Test

## Prompt

```text
Pressure-test my portfolio sitemap against my proof statement and one main action.

Proof statement:
I want my portfolio to prove that I am a backend-focused full-stack developer who can build clean, reliable, real-world systems with strong UI/UX awareness.

One main action:
I want visitors to contact me or view my GitHub projects.

Sitemap:
Home

- Hero: name, role, proof statement, GitHub/contact CTA
- Featured Work: APoS, LUMEN, EXPY, CodeGuard AI
- About: IT student, backend/full-stack focus, design background
- Contact: GitHub, LinkedIn, email

Tell me:

1. Which sections earn their place?
2. Which sections are weak or unnecessary?
3. What should I change before building?
```

## Codex Output

### 1. Which sections earn their place?

All four sections earn their place because each one supports the proof statement and the main action.

The Hero earns its place because it quickly tells visitors who you are, what you do, and what action they should take. It should immediately say that you are a backend-focused full-stack developer, not just a student or general creative.

Featured Work is the strongest section. This is where you prove the claim. APoS, LUMEN, EXPY, and CodeGuard AI should not just be listed as projects. Each one should show what problem it solves, what stack you used, what backend work you handled, and what makes it reliable or real-world.

About earns its place if it stays short. It should explain your background only as it supports the claim: IT student, backend/full-stack focus, UI/UX awareness, and ability to build complete systems.

Contact earns its place because it supports the one main action. It should make GitHub, email, and LinkedIn easy to find.

### 2. Which sections are weak or unnecessary?

No section is unnecessary, but some parts are weak if written too generally.

The weak part is the About section if it becomes a life story. Keep it focused on credibility, not biography.

The Featured Work section is weak if it only shows project names, screenshots, and tech badges. That would not prove backend engineering. It needs proof of architecture, database work, APIs, auth, persistence, scraping, or system logic.

The Hero is weak if it says something generic like "Full-stack Developer and Designer." That sounds broad. The claim is stronger if it says backend-focused full-stack developer with UI/UX awareness.

### 3. What should change before building?

Change the sitemap from a simple section list into a proof-focused flow:

```text
Home
- Hero: backend-focused full-stack developer + GitHub/contact CTA
- Proof / Featured Work:
  - APoS: ordering system, backend/API/database role
  - LUMEN: productivity system, scheduling/task logic
  - EXPY: finance tracker, transaction/category/alert logic
  - CodeGuard AI: security/static analysis/AI remediation
- About: short credibility summary
- Contact: GitHub, LinkedIn, email
```

For each project, use this structure:

```text
Project name
Problem it solves
My role
Stack used
Backend/system proof
GitHub/demo link
```

## Change I Will Make

I will make the Featured Work section proof-based instead of project-name-based by showing the problem, stack, backend role, and system behavior for each project.
