## Case 1: APoS

### The Problem

Campus pre-ordering can get messy when the ordering flow is slow, unclear, or not built well for mobile use. APoS needed to make ordering feel direct: browse, choose, place the order, and track what happens without making the user think too much.

### What I Did

I worked on a web and mobile pre-order system with a mobile-first interface, real-time interaction, and a smoother ordering flow. My decisions focused on the parts that make the system usable in practice: responsive screens, clear order states, fast menu browsing, and UI patterns that work on small screens. I treated the interface and system behavior as one problem instead of separating "design" from "backend."

### What Came Of It

APoS became a clearer proof piece for real-world product workflow: ordering, state changes, and user-facing feedback. It shows that I can build around an actual user task, not just make static screens.

## Case 2: LUMEN

### The Problem

Students often split their schedule, tasks, and workload planning across different tools. That makes it harder to see what needs attention and what is becoming too heavy.

### What I Did

I built LUMEN as a full-stack student productivity application for scheduling, task management, productivity tracking, and workload visibility. I worked on smart scheduling, calendar integration, task flow, and analytics that make the user's workload easier to understand. I also cared about the UI quality because productivity software fails when it feels heavy or confusing.

### What Came Of It

LUMEN proves that I can turn a broad problem into organized product areas: schedules, tasks, analytics, and interface flow. It supports my portfolio claim because the work is not only visual; it depends on system logic and clear data structure.

## Case 3: EXPY

### The Problem

Expense tracking needs more than a form and a chart. Users need a reliable way to record transactions, organize categories, notice thresholds, and understand spending patterns.

### What I Did

I developed EXPY around a client-server structure for financial tracking. I worked on transaction management, categories, threshold alerts, backend logic, and financial insight features. The key decision was to keep the system organized around real user behavior: what money came in or out, what category it belongs to, and when the app should warn the user.

### What Came Of It

EXPY became a practical backend-focused project because it deals with structured data, validation, user behavior, and meaningful reporting. It shows that I can build systems where the data model matters.

## Case 4: CodeGuard AI / Compass AI

### The Problem

Developers entering an unfamiliar codebase need to understand dependencies quickly, and they also need help spotting risky code patterns before those patterns become bigger problems.

### What I Did

For the IBM BOB Hackathon 2026 Team AVON project, I contributed backend development and security research for an AI-powered developer onboarding and code analysis platform. The work included dependency map ideas, OWASP-focused vulnerability detection, cross-file analysis thinking, and AI-assisted remediation using IBM WatsonX, FastAPI, and Next.js. My role was to help make the system useful for developers, not just impressive as an AI demo.

### What Came Of It

The project became proof that I can work with backend logic, security concerns, and AI integration under hackathon constraints. It also gives my portfolio a stronger signal than a normal class project because the work had a real technical problem and team delivery pressure.
